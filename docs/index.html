The Albert Framework Guide

Albert (Composer package albert/framework, PSR-4 namespace Albert\) is a small PHP framework: a DI container, an event dispatcher, a router with a middleware pipeline, a minimal database layer, Twig views, and a CLI. This guide covers exactly what exists today and how the pieces fit together.

01 — Orientation

Overview

Every request runs through one object, the Kernel. It owns three collaborators — a Container, an EventListener, and a Router — and turns an incoming HTTP request into a response by matching a route, running middleware, and calling a controller or closure.

There's no ORM, no auth layer, and no scaffolding beyond a controller generator yet — this is an early, honest MVP, not a Laravel clone. What's here is small enough to read end to end in an afternoon.

02 — Orientation

Quick start

Composer's config lives in src/, not the repo root — run every Composer and PHPUnit command from inside src/. There's no local php or composer binary assumed, so the commands below run through Docker.

terminal
cd src
composer install

# copy the example env (sqlite by default, no extra services needed)
cp .env.example .env

# serve on http://localhost:8000
docker run --rm -p 8000:8000 -v "$PWD:/app" -w /app \
  php:8.4-cli php -S 0.0.0.0:8000 index.php

Visiting / renders the Twig welcome view; /hello/{name} echoes the route parameter back as plain text — both wired in routes/web.php against HomeController.

Full stack instead: docker-compose up --build from the repo root starts nginx + php-fpm on port 80, using src/ as the webroot.
03 — Orientation

Project structure

Everything Composer sees lives under src/. The PSR-4 root Albert\ maps straight onto it, so a namespace segment is a directory of the same name and case.

src/
src/
├── bootstrap.php        // builds the wired Kernel — required by both entry points
├── index.php             // HTTP entry point: bootstrap + $kernel->run()
├── bin/console            // CLI entry point (Symfony Console)
├── routes/web.php         // route table, receives the Router
├── Core/                  // Container, EventListener, Kernel
├── Http/                  // Router, Route, MiddlewareInterface, Controllers/, Middleware/
├── Database/               // Connection, Model
├── View/                  // View (Twig wrapper)
├── Console/Commands/       // route:list, make:controller
├── resources/views/        // Twig templates
├── storage/                // default sqlite database lives here
└── tests/                 // PHPUnit, mirrors the src/ tree
Case matters. This repo is developed on a case-insensitive filesystem (macOS). A CLI entry point was once named console directly under src/ and silently collided with the Console/ namespace directory — that's why the entry point lives at bin/console instead. The same reasoning keeps the default SQLite path under storage/, never database/, which would collide with Database/.
04 — Request lifecycle

Architecture

The Kernel constructs (or accepts) a Container, EventListener, and Router, then registers all three — plus itself — into the container so any class can type-hint them and have them autowired.

Kernel
Container
bind / singleton / instance, autowires constructors
EventListener
listen / dispatch pub-sub
Router
registers & matches routes

Handling a request is Kernel::handle(): match a route, bind its {param} values onto $request->attributes, run the middleware pipeline, then call the action. A non-Response return value is wrapped in a plain Response automatically.

Request
from PHP globals
→
Router::match()
first method+path hit, else 404
→
Middleware
global + per-route, onion order
→
Action
controller method or closure
→
Response
sent to the client

Three events fire around the whole cycle, each carrying the request (and, where relevant, the response or exception) as payload: kernel.handling, kernel.handled, and kernel.exception. Any uncaught Throwable becomes a 500 — the real message is only shown when APP_DEBUG=true.

05 — Request lifecycle

Routing

Routes are registered against the Router inside routes/web.php, a closure that the bootstrap process calls with the kernel's router instance.

src/routes/web.php
return function (Router $router): void {
    $router->get('/', [HomeController::class, 'index'], 'home');
    $router->get('/hello/{name}', [HomeController::class, 'hello'], 'hello');
};

get(), post(), put(), patch(), and delete() all take a URI, an action (a [ControllerClass::class, 'method'] pair or a closure), and an optional route name. Each returns the Route, so you can chain ->middleware() straight off the registration.

A {param} segment becomes a named capture group — /hello/{name} matches /hello/Ada and exposes name => 'Ada' on $request->attributes. Router::match() returns the first route whose method and path both match, trailing slashes ignored; no match falls through to a plain 404 in the kernel.

06 — Request lifecycle

Middleware

Middleware implements one method, handle(Request $request, Closure $next): Response, and can inspect or rewrite the request on the way in and the response on the way out.

src/Http/Middleware/AddHeaderMiddleware.php
class AddHeaderMiddleware implements MiddlewareInterface
{
    public function handle(Request $request, Closure $next): Response
    {
        $response = $next($request);
        $response->headers->set('X-Powered-By', 'Albert');

        return $response;
    }
}

Register middleware two ways — globally, so it wraps every route, or per-route, so it only wraps that one:

bootstrap.php / routes/web.php
// global — applies to every request
$kernel->pushMiddleware(new AddHeaderMiddleware());

// per-route — instance or a container-resolvable class string
$router->get('/admin', [AdminController::class, 'index'])
    ->middleware(AuthMiddleware::class);

Global middleware runs first and wraps everything inside it — including route-specific middleware and, at the very center, the controller action itself:

GLOBAL MIDDLEWARE (registered order)
ROUTE MIDDLEWARE
Controller action / closure
07 — Core services

Container (dependency injection)

Container implements PSR-11's ContainerInterface. Three ways to register something, and one way to get it back out:

MethodBehavior
bind($abstract, $concrete = null)A new instance is built every time it's resolved.
singleton($abstract, $concrete = null)Built once, then the same instance is reused.
instance($abstract, $object)Registers an object you already built.
get($id) / resolve($id)Returns the resolved instance, autowiring if nothing was registered.

Anything not explicitly registered is still resolvable if it's a concrete, instantiable class: the container reflects its constructor and recursively resolves each typed, non-builtin parameter. A parameter with a default value falls back to that default; anything else unresolvable throws RuntimeException.

example
// HomeController's constructor takes a View — resolved automatically
class HomeController
{
    public function __construct(private readonly View $view) {}
}

$controller = $container->get(HomeController::class); // just works

The kernel pre-registers itself and its three collaborators as instances — Container::class, EventListener::class, Router::class, and Kernel::class — so any autowired class can simply type-hint them.

08 — Core services

Events

EventListener is a small, synchronous pub/sub bus — string event names, no event objects required.

example
$events = $kernel->events();

$events->listen('kernel.handled', function (Request $request, Response $response) {
    error_log($request->getPathInfo() . ' -> ' . $response->getStatusCode());
});

$events->dispatch('kernel.handled', $request, $response); // returns each listener's return value as an array
$events->hasListeners('kernel.handled'); // true
$events->forget('kernel.handled');      // remove all listeners for the event

The kernel dispatches three events on every request: kernel.handling (request only, before matching), kernel.exception (request + the thrown exception, only on failure), and kernel.handled (request + the final response).

09 — Core services

Database & models

Connection::fromEnv() builds a Doctrine DBAL connection from environment variables. With nothing set, it defaults to zero-config SQLite at storage/database.sqlite, creating the directory if needed. Set DB_CONNECTION to anything else to switch to MySQL/Postgres/etc. via DB_DRIVER/DB_HOST/DB_PORT/DB_DATABASE/DB_USERNAME/DB_PASSWORD.

Model is a minimal Active Record base — no relationships, casting, eager loading, or migrations. A subclass sets a table name and gets basic CRUD for free:

example
class Post extends Model
{
    protected static string $table = 'posts';
}

Post::all();                       // static[] — every row
Post::find(1);                     // static|null — by primary key
Post::where('author', 'Ada');       // static[] — equality filter

$post = Post::create(['title' => 'Hi']); // insert, returns the new row
$post->title = 'Updated';
$post->save();                     // insert if no id set yet, else update
$post->delete();

Attributes are read and written dynamically ($post->title) via __get/__set over an internal $attributes array — there's no schema declaration on the model itself. Call Model::setConnection() once at bootstrap before any model is used; bootstrap.php already does this.

10 — Core services

Views (Twig)

View is a thin wrapper around a Twig Environment reading templates from src/resources/views/.

example
class HomeController
{
    public function __construct(private readonly View $view) {}

    public function index(Request $request): Response
    {
        return new Response($this->view->render('welcome.twig', ['name' => 'World']));
    }
}

Registered into the container as an instance in bootstrap.php, with Twig's debug mode following APP_DEBUG. Call $view->environment() to reach the underlying Twig Environment directly — for adding filters or globals, for example.

11 — Tooling

CLI commands

The CLI entry point is src/bin/console, a Symfony Console Application that loads the same wired Kernel as the HTTP entry point.

terminal — run from src/
docker run --rm -v "$PWD:/app" -w /app php:8.4-cli php bin/console route:list
docker run --rm -v "$PWD:/app" -w /app php:8.4-cli php bin/console make:controller PostController
CommandWhat it does
route:listPrints every registered route as a table — method, URI, name, and controller@method or Closure.
make:controller {name}Scaffolds a plain controller class with one index() action into Http/Controllers/. Refuses to overwrite an existing file.

What's not built yet

Albert follows a 12-phase roadmap (src/todo.md); phases 1–7 are done at MVP scope. Don't assume a feature below exists just because a similarly-named piece does in Laravel or another framework.

✓
Routing & middlewareMethod-based routes, {param} segments, named routes, an onion-style middleware pipeline.
✓
Database layerDoctrine DBAL connection + a minimal Active Record base.
✓
TemplatingTwig, wired through View.
✓
CLIroute:list and make:controller on Symfony Console.
○
Full ORMNo relationships, migrations, casting, or eager loading — Model is CRUD only.
○
Broader scaffoldingOnly controller generation exists; no model/migration/test generators.
○
Auth & securityNo authentication, authorization, or session handling of any kind yet.
○
Example appsOne demo route (HomeController) — no larger reference application.
○
Formal docs & packagingThis page aside, no published docs site, and no deployment tooling beyond the included Dockerfiles.

For the long-term target shape — a layered Application / Domain / Infrastructure / Framework Core architecture — see src/Nexus Framework: Architecture and Design Specification.md in the repo. "Nexus" is that design doc's working title; the shipped package is albert/framework.
